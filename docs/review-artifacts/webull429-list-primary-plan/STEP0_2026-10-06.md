Proposed plan, subject to approval/verification rather than an implemented fix:

1. Ordinary reads share one **logical listing** per real account/cycle, with
   coalescing across callers. Every page is a separate budgeted HTTP request.
   Keep2s cache semantics and expose page acquisition times, completeness,
   continuation cursor and account/session identity. Cache matched positive
   rows; never cache errored/truncated traversal as affirmative absence.
2. Proposed conservative query limiter: **at most2 HTTP requests per rolling2s
   per app key/endpoint**, across threads/accounts and including page/confirmation
   requests. This is a proposed ceiling, not a confirmed legacy quota. Propose
   at most2 list page requests per account cycle initially; any continuation
   must be fair and its detection latency measured before approval. A20-page
   scan needs roughly18s minimum even with ideal bursts, so cannot be promised
   complete inside the current15s cycle. Do not merely let the 2s cache expire
   halfway through a pass and start another unbudgeted scan.
3. Exact account/client ownership remains mandatory; derive T/S/M from the
   durable owned base, never adopt by symbol/prefix/position. Reject conflicting
   row identity. List HTTP success, usable fields and per-row age must be
   validated. Missing target, even in a complete list, is UNKNOWN, not account
   flatness or cancellation. Missing prior-day GTC orders also remain unknown.
4. An optional terminal detail probe means **one concurrent budgeted attempt
   per terminal evidence version**, not a permanent attempted flag. Persist
   completed proof bound to account/client/broker order, source, acquisition
   time, status and fill quantity/price/broker timestamp. Crash before commit
   permits re-read; crash after commit uses idempotent durable attribution.
   Probe429 never becomes completed proof. Partial fills remain nonterminal;
   account their fills without releasing remaining ownership/protection.
5. A complete, validated exact-client list execution can remain usable if the
   optional detail probe429s. Do not expand a mere matching string into fill or
   cancel proof. Preserve first-valid-FILLED OCO return and fresh both-child EOD
   confirmation. A stale/nonterminal cached row must not clear a reservation.
6. **OUT OF BUILD SCOPE / deferred only:** the specific cancel429 cause is
   DISAGREE within captured coverage. No cancel-code build is authorized by
   this Step0. If future independent positive evidence opens that lane, a
   defensive proposal would be no more than **one additional POST per
   exact client**, default2s backoff, **6s total operation deadline** including
   readback/network time. Before a duplicate POST after an uncertain outcome,
   obtain fresh exact-client readback and ensure no earlier POST remains in
   flight. Known terminal suppresses repeat; known working can permit a bounded
   retry. Missing/unreadable does not authorize release/sell. A real Retry-After
   beyond the remaining deadline defers the operation and retains UNKNOWN.
   Retain existing10s uncertainty scheduling and accepted-cancel evidence rules.
7. Detail budget sharing must not silently relax strict RPG proof or deadline
   rules. Whether priority/reservation can honor those rules under simultaneous
